# Ephemeral preview environments

A GitOps pipeline whose trigger is **PR preview** stands up an environment of its own for
each open pull request, deploys the branch into it, posts the URL back to the pull request,
and destroys it on merge, close or expiry, whichever comes first.

Permission keys on this page: `gitops.view`, `gitops.manage`, `gitops.delete`,
`environments.manage`.

## What authenticates a delivery

`POST /api/webhooks/gitops/pr` is mounted without a session, because a forge cannot present
one. What authenticates it is an **HMAC-SHA256 over the raw request body**, verified against
a secret stored on the repository row.

- The secret is generated by `POST /api/gitops/repos/{repoId}/webhook-secret`
  (`gitops.manage`) and is returned **once**, in that response and nowhere else. It is
  encrypted at rest and no later response contains it. Calling the route again rotates it,
  which invalidates the value the forge currently holds.
- `GET /api/gitops/repos/{repoId}/webhook-secret` (`gitops.view`) answers only
  `{"configured": true|false}`.
- `DELETE` on the same path (`gitops.manage`) removes it, which **refuses** every subsequent
  delivery for that repository rather than falling back to accepting unsigned ones.
- **A repository with no secret has its deliveries refused**, with a 401 and a server log
  line naming the repository. This is deliberate: an endpoint that accepts anything is not a
  gate.

The repository is named by `?repo=<id>` on the webhook URL, or by `repoId` in a native
McHarbor payload. It is read before verification only to decide which secret to verify
against; nothing is acted on until the HMAC over those exact bytes matches.

### Configuring each forge

| Forge | URL | Header McHarbor reads |
|---|---|---|
| GitHub | `https://<host>/api/webhooks/gitops/pr?repo=<repoId>` | `X-Hub-Signature-256` (secret set as the webhook secret) |
| Gitea | same | `X-Hub-Signature-256` or `X-Gitea-Signature` |
| GitLab | same | `X-Gitlab-Token` set to the secret itself |

Real GitHub, GitLab and Gitea pull-request bodies are accepted directly. Actions the
lifecycle does not care about (`labeled`, `edited`, `assigned`, `ready_for_review` and the
rest) return **200**, so the forge's delivery log stays clean.

## What a pipeline configures

| Field | Default | What it does |
|---|---|---|
| `preview.ttlHours` | 72 | How long a preview lives. Clamped to 168 hours (7 days). |
| `preview.maxConcurrent` | 5 | How many previews this pipeline may run at once. `0` means no cap. |
| `preview.hostnameTemplate` | `pr-{number}.{domain}` | Placeholders: `{number}`, `{branch}`, `{pipeline}`, `{domain}`. |
| `preview.baseDomain` | empty | Your own wildcard record. McHarbor manages no DNS. |
| `preview.ownerUserId` | empty | The principal whose `environments.manage` is checked before an environment is created. **Required**: a pipeline without one refuses to provision. |
| `preview.commentEnabled` | true | Whether to post the URL back to the pull request. |

With no `baseDomain` and no template there is simply **no URL**, and the preview shows the
environment rather than a hostname that does not resolve.

## Quotas belong to the pipeline

The concurrency cap is a property of the pipeline, not of the environment, so one busy
repository cannot exhaust the host and starve another. It is enforced at **admission**: the
(N+1)th pull request gets a preview row with status `refused`, the reason recorded on the
row, a comment on the pull request saying so, and **no environment created**.

## Permissions

| Action | Key |
|---|---|
| See previews | `gitops.view` |
| Configure a pipeline's preview policy, generate or clear a webhook secret | `gitops.manage` |
| Destroy a preview before its TTL (`DELETE /api/gitops/previews/{id}`) | `gitops.delete` |
| Create the preview's environment | `environments.manage`, checked against `preview.ownerUserId` |

The webhook carries no principal, which is why the environment is attributed to the
pipeline's configured owner. A pipeline with no owner, or an owner without
`environments.manage`, leaves the preview `failed` with that reason on the row rather than
creating anything.

## What runs inside a preview

Once the environment exists, the pipeline's `pr_preview` stage is promoted into it: the
pull request's head commit is fetched, the stage's **Compose path** is read from it, and
it is deployed as the stack `preview-<pipeline>-pr-<number>`, owned by that preview. A new
commit on the pull request redeploys the same stack. See
[Promotions and deploys](../promotions/README.md) for the fetch, the limits and what is recorded.

The webhook answers as soon as the environment exists; the fetch and the deploy run in the
background, so a forge's delivery timeout never cuts a deploy short. The pull-request
comment is posted once the stack is up, not before. A deploy that fails leaves the preview
`failed` with Compose's own message behind the error icon beside the status.

A pipeline with no `pr_preview` stage still creates the environment and deploys nothing
into it.

## Lifecycle and statuses

| Status | Means |
|---|---|
| `active` | Up, inside its TTL |
| `demolishing` | Teardown started. A restart in the middle is finished on the next tick. |
| `demolished` | Torn down because the pull request closed or merged, or on request |
| `expired` | Torn down because the TTL ran out |
| `failed` | Creation or deployment failed; the reason is on the row |
| `refused` | The pipeline's concurrency cap was already full |

A merge is distinguishable from a close: `tornDownBy` reads `pr-merged` or `pr-closed`. A
reopened pull request resurrects its preview with a fresh environment and a fresh expiry.

## Cleanup

The reaper is a branch in the GitOps scheduler's existing 60-second tick, leader-gated in an
HA cluster. Everything it acts on is a persisted column, so it survives a restart. Per tick
it handles, in order:

1. a teardown interrupted mid-flight (`demolishing`);
2. a preview past its persisted `expiresAt`;
3. a creation that half-failed: no environment 15 minutes after the row was written, or a
   recorded failure;
4. a preview whose repository has been deleted;
5. a pull request that was closed, merged or deleted while its webhook was missed (see
   [The forge probe](#the-forge-probe)).

Teardown brings the preview's stack down, with its volumes, **before** the environment is
deleted. If the stack cannot be removed, the environment is left in place, the preview
stays `demolishing` with the reason on the row, and the next tick tries again. An
environment is never deleted over containers that are still running.

Separately, an ephemeral environment whose preview row has been cascade-deleted with its
pipeline is collected by the expiry stamped on the environment itself, so an orphan still
has an owner.

**The reaper will never delete an environment it did not create.** An environment created
for a preview carries `ephemeral = 1` and the preview's id; teardown checks both before
deleting anything. An environment a preview row merely points at (one an operator pointed a
stage at, for instance) is left in place and the refusal is recorded on the preview row,
where it shows behind the error icon beside the status.

Teardown is idempotent. Destroying a preview twice is success, not an error.

## The forge probe

On each tick the reaper asks the forge about up to **5** active previews, each at most once
every **10 minutes**, using the repository's stored credential:

| Forge | Request |
|---|---|
| GitHub | `GET https://api.github.com/repos/<owner>/<repo>/pulls/<number>` |
| GitLab | `GET <host>/api/v4/projects/<path>/merge_requests/<number>` |
| Gitea | `GET <host>/api/v1/repos/<owner>/<repo>/pulls/<number>` |

It destroys a preview **only** on a definite answer:

| The forge answers | The probe |
|---|---|
| 200, the pull request is closed | destroys it, `tornDownBy` = `pr-closed` |
| 200, the pull request is merged | destroys it, `tornDownBy` = `pr-merged` |
| 404, **and** the repository itself answers 200 with the same credential | destroys it, `tornDownBy` = `pr-not-found` |
| 200, still open | nothing |
| 404 while the repository is not visible either | nothing; GitHub and GitLab answer 404 for a private repository the token cannot read |
| 401, 403, 429, 5xx, a timeout, no credential | nothing; the server log says why |

A repository with no stored credential is never asked at all: an unauthenticated answer
cannot tell "gone" from "not allowed to see". Those previews are collected by their TTL.

## What goes wrong

| Symptom | Cause |
|---|---|
| Preview is `failed` with "deploying the preview failed: …" | The deploy failed; the rest of the sentence is the reason. See [Promotions and deploys](../promotions/README.md#what-goes-wrong) |
| Preview stays `demolishing` with "removing stack … failed" | The stack could not be brought down; the environment is kept until it can |
| Every delivery shows 401 in the forge | No webhook secret for that repository, or the secret was rotated and the forge still holds the old one |
| Deliveries 400 with "repo missing" | The webhook URL has no `?repo=<id>` and the body is not a native McHarbor payload |
| Preview is `failed` with "does not hold environments.manage" | `preview.ownerUserId` names a principal without the key |
| Preview is `failed` with "no preview owner is configured" | The pipeline has no `preview.ownerUserId` |
| Preview is `refused` | The pipeline's `preview.maxConcurrent` is already in use |
| Preview has no URL | The pipeline has no `preview.baseDomain` and no hostname template |
| The comment never appeared | The repository has no stored credential, or the forge refused it. This never fails the preview; the reason is on the row |

## Known limits

- **Only the Compose file is deployed.** Build contexts and files beside it are not; see
  [Promotions and deploys](../promotions/README.md#known-limits).
- **No data seeding.** Deliberately out of scope for this landing.
- A preview whose pull request was closed while McHarbor was down is collected by the
  forge probe within minutes when the repository has a credential, and by its TTL when it
  has none.
