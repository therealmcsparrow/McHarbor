# terraform-provider-mcharbor

A Terraform provider for McHarbor, built on the Terraform plugin framework. It talks to McHarbor's
HTTP API through a client generated from the committed OpenAPI document
(`src/backend/api/openapi.json`), so every request shape comes from the router that actually runs.

It manages environments, stacks, roles, role assignments, API keys, secrets, schedules, update
policies, alert rules, storage locations, backup plans, workflows and plugins, and reads
environments, roles, the permission catalog, secrets, containers, images, the app catalog and the
plugin catalog.
The reference, with the permission key each operation needs, is in
[`.documentation/terraform/`](../../.documentation/terraform/README.md).

## Build and install locally

```bash
cd src/terraform-provider-mcharbor
GOWORK=off go build -o terraform-provider-mcharbor .
```

Point Terraform at the binary with a development override in `~/.terraformrc`
(`%APPDATA%\terraform.rc` on Windows):

```hcl
provider_installation {
  dev_overrides {
    "therealmcsparrow/mcharbor" = "/path/to/src/terraform-provider-mcharbor"
  }
  direct {}
}
```

With an override in place, skip `terraform init` and run `terraform plan` directly.

## Authentication

Create an API key in McHarbor under **Security → API Keys**. The key acts with the roles you give it,
so it needs every permission the resources you manage require (see the reference). Then:

```hcl
provider "mcharbor" {
  endpoint = "https://mcharbor.example:8705"
  # api_key = ...            or MCHARBOR_API_KEY
  # insecure_skip_verify = true   only for the default self-signed certificate
}
```

`endpoint` falls back to `MCHARBOR_ENDPOINT` and `api_key` to `MCHARBOR_API_KEY`. Prefer the
environment variable for the key, so it never appears in configuration.

McHarbor serves HTTPS with a self-signed certificate by default. Either trust its CA on the machine
running Terraform (preferred) or set `insecure_skip_verify = true`.

When McHarbor refuses a request with 403, the error names the permission key the operation requires,
for example `McHarbor refused rolesCreate (HTTP 403): Permission denied. The API key needs the
permission roles.manage`.

## What lands in Terraform state

Terraform state stores every attribute in plain text. Protect it (an encrypted remote backend,
restricted access) as you would the secrets themselves. Per resource:

| Resource | Secret material in state | Notes |
|---|---|---|
| `mcharbor_environment` | `ssh_key`, `tls_ca`, `tls_cert`, `tls_key` as configured; `agent_token` for `connection_type = "agent"` | The agent token is returned once, at creation. The TLS and SSH values are never read back from McHarbor, so a change made in the UI is not detected. |
| `mcharbor_stack` | `env_vars` | McHarbor masks secret variables on read. A masked value keeps the configured one, so a secret changed in the UI is not detected. Prefer `${secret:NAME}` references to McHarbor's secrets vault over literal values. |
| `mcharbor_role` | none | |
| `mcharbor_role_assignment` | none | |
| `mcharbor_api_key` | `key` | Returned once at creation. After `terraform import` it is null, because McHarbor never shows it again. |
| `mcharbor_secret` | none | The value is write-only (`value_wo`, Terraform 1.11+) or generated by McHarbor and discarded; bump `value_wo_version` to rotate. |
| `mcharbor_storage_location` | none | Credentials (`*_wo`) and `config_wo` are write-only, re-sent when `credentials_version` changes. |
| `mcharbor_schedule`, `mcharbor_update_policy`, `mcharbor_alert_rule`, `mcharbor_backup_plan` | none | |
| `mcharbor_workflow` | whatever the canvas holds | Node settings are stored as written. Reference McHarbor secrets from nodes instead of pasting values into the canvas. |
| `mcharbor_plugin` | none | Plugin settings are not managed by Terraform. |

## Behaviour worth knowing

- **Destroying an API key revokes it.** McHarbor keeps the revoked row for audit, and the provider
  treats a revoked key as gone.
- **Role assignments are never edited.** Changing any attribute replaces the assignment.
- **Changing an environment's `connection_type` replaces it.** McHarbor's in-place connection
  migration is a guided UI flow and is not exposed here.
- **`auto_start` on a stack is read only at creation.** An agent environment has no connected agent
  on the first apply, so create its stacks with `auto_start = false` and deploy once the agent has
  checked in, as `examples/complete` does.
- **Workflows are JSON files, not HCL.** Export the canvas from the workflow editor and pass it with
  `file("workflow.json")`. Reformatting the file is not a change.
- **A plugin is pinned to an exact catalog version.** Changing `version` runs the same
  uninstall-and-install cycle as a Store update; settings and role grants are kept. Destroying the
  resource keeps the plugin's data unless `purge_on_destroy = true`.
- **System roles** (`is_system = true`) cannot be changed or deleted, and McHarbor refuses the request.

## Development

```bash
GOWORK=off go generate ./...    # regenerate the client and the permission map from the spec
GOWORK=off go vet ./...
GOWORK=off go test ./...        # unit tests; acceptance tests skip
TF_ACC=1 MCHARBOR_ENDPOINT=https://localhost:8705 MCHARBOR_API_KEY=... \
  MCHARBOR_INSECURE_SKIP_VERIFY=1 GOWORK=off go test ./internal/provider/ -run TestAcc -v
```

Acceptance tests need a `terraform` binary on `PATH` and an instance they may create and delete roles
on. Regenerate after any change to `src/backend/api/openapi.json`. Both generators are deterministic,
so an unchanged spec produces byte-identical files.

The provider has its own version sequence in McHarbor's calendar notation, set at build time with
`-ldflags "-X main.version=2026.09.01"`. It does not move when McHarbor releases.
